# 开发计划：官方场地实战仿真（field_sim）

本计划记录下一阶段的三项工作。三项按顺序开发，**每完成一项就提交并推送一次**。
已有的各个模式（沙盒、目标区、分层移动、战术、多机、规则实验对局）和 `rules/` 规则模块保持不变，
新工作放在一个独立的新模式 `field_sim/` 里，状态、回放与构建 ID 互不混用。

| # | 内容 | 状态 |
|---|---|---|
| 1 | 官方场地 1:1 复刻模拟 | **已完成**（见 [field_sim/README.md](../field_sim/README.md)） |
| 2 | 车辆参数配置化、默认参数与“车库”（保存整车、下次直接选用） | **已完成**（见 [field_sim/VEHICLES.md](../field_sim/VEHICLES.md)） |
| 3 | 机器人对外接口：感知数据 + 控制指令，可用外部代码控制 | 待开发 |

## 总体结构

```
field_sim/
  field/rmuc2027_v1/   官方场地数据（由官方 STEP 提取）+ 来源记录
  vehicles/            内置默认车辆配置
  *.hpp / *.cpp        C++ 权威引擎（地形、底盘、云台、发射、弹道、感知、裁判数据）
  bridge.py            Python 桥接（引擎进程、车库、对局配置）
  control_server.py    对外控制接口（本机 TCP，逐行 JSON）
  sdk/                 外部控制代码用的客户端与示例
web/field.html         场地与对局观察页面
web/garage.html        车辆配置与车库页面
tools/field_extract/   从官方 STEP 生成场地数据的离线工具（仅开发时使用）
```

沿用仓库已有约定：C++ 引擎是唯一权威，Python 只做本机桥接，浏览器只显示；
运行时不新增第三方依赖（只需要 C++20 编译器与 Python 标准库）；每一项都带原生测试和接口测试，
并在 `docs/VERIFICATION.md` 记录实际运行结果；所有不是来自官方资料的数值都明确标注为工程假设。

## 第 1 项：官方场地 1:1 复刻模拟

**目标**：机器人在与官方场地同尺寸、同高度、同结构的战场上行驶和交战，而不是在演示矩形里。

资料来源：

- 官方开源场地模型 `RMUC2027_V1.0.0.stp`（[RMU 2027 场地图纸开源帖](https://bbs.robomaster.com/article/1970956)，
  653,443,279 字节，MD5 `3d3d6a411f44e9a4983794261b3f0bf7`）。文件太大，不放进仓库，只记录地址与校验值。
- 《RMUC 2027 比赛规则手册 V1.0.0》第 4 章图纸（图 4-5 定位尺寸、图 4-27 中央高地、图 4-35 公路区等）
  与 §5.6.4 增益点定义，用来核对提取结果并标注功能区。

要做的事：

1. **提取工具**：读取官方 STEP，按装配关系还原到战场坐标系（长边 28 m 为 X，宽 15 m 为 Y，战场地面为 Z=0），
   三角化后按 20 mm 网格采样成高度场。每个格子记录地面高度；有隧道、桥面等悬空结构的地方另记
   “下表面高度 / 上表面高度”，这样既能从隧道里穿过去，也能从上面跨过去。
2. **场地数据**：高度场 + 功能区（启动区、补给区、基地、前哨站、堡垒、制高点、梯形高地、中央高地、
   装配区、公路、隧道、起伏路段、能量机关、增益点与禁区）+ 来源记录。红蓝双方按中心对称核对。
3. **核对**：把提取结果与手册标注尺寸逐项比较（28000 × 15000、各模块定位尺寸、高地高度、坡度等），
   偏差写进验证记录；对不上的地方按手册“以规则手册和现场为准”的说明处理并注明。
4. **引擎地形模型**：机器人沿高度场行驶——坡道按坡度爬升，超过车辆越障能力的台阶视为墙，
   可以从台地边缘驶下或飞坡落地，隧道按车高判断能否通过；弹丸按三维弹道飞行并被地形遮挡；
   视线判断同样基于高度场。
5. **观察页面**：`field.html` 画出官方场地俯视图（高度着色 + 功能区），可以开一辆车在场地里行驶。

验收：场地外廓与手册尺寸一致；关键结构的位置、高度与手册标注的偏差在手册公差（±5%）内，或已逐项说明；
车辆能在公路、坡道、高地、隧道间按预期通行，墙体不可穿越；原生测试覆盖地形查询、通行、遮挡。

已知边界：战场 1°~2° 的整体倾斜、50 mm 回收开槽、风机等细节按 STEP 中的实际建模处理，
若 STEP 没有体现则不额外添加；能量机关、基地、前哨站等道具先按占位体积处理碰撞，其机制在第 3 项接入。

## 第 2 项：车辆参数配置化与车库

**目标**：每辆车的参数都能配置，有一套默认值；配好的整车可以保存，下次模拟直接选用。

1. **车辆配置格式** `rmuc-vehicle.v1`（JSON，严格校验），分为：
   - 基本信息：名称、兵种（重装 / 步兵 / 哨兵）、备注；
   - 底盘：驱动形式（全向 / 麦轮、差速、舵轮、平衡）、长宽高、质量、轮距轴距、最高速度、
     加速度、最大角速度、越障高度、可爬坡度、功率控制方式；
   - 云台：俯仰 / 偏航范围、最大角速度与角加速度、枪口位置；
   - 发射机构：口径、设定初速度及其波动、射频上限、散布；
   - 装甲：各装甲模块的位置、朝向与尺寸；
   - 感知：相机视场角、识别距离、帧率、延迟、测量噪声，可选的激光雷达；
   - 规则属性选择：步兵的底盘类型 / 发射机构类型、哨兵自动 / 半自动等，
     血量、热量、功率上限等由规则模块按选择给出，不允许随意填写。
2. **默认车辆**：重装、步兵（若干典型构型）、哨兵各一套默认参数，随仓库提供，只读。
   默认值中来自规则手册的部分注明出处，其余是工程假设。
3. **车库**：保存、另存、改名、删除、导入 / 导出整车配置；配置保存在本机 `user_data/vehicles/`
   （不进版本库），服务重启后仍在。
4. **对局配置**：每个出场位置选择一辆车库里的车（或默认车）和控制方式；对局记录绑定所用车辆配置的哈希。
5. **页面**：`garage.html` 编辑与管理车辆；`field.html` 开局前按位置选车。

验收：修改参数后车辆行为随之改变（例如最高速度、云台转速、越障高度）；保存的车辆在重启服务后可直接选用；
非法或越界的配置被拒绝并说明原因；有接口测试与原生测试。

## 第 3 项：机器人对外接口（感知 + 控制）

**目标**：用外部代码（任意语言）控制场上的机器人，拿到的信息和能下发的指令尽量贴近真实赛场上
机器人自身程序所处的条件——只知道自己的传感器和裁判系统告诉它的东西。

1. **机器人向外提供的数据**（按真实来源分组）：
   - 自身状态：位置与朝向、速度、姿态（俯仰 / 横滚 / 偏航）与角速度、加速度、云台角度与角速度、
     轮速里程计；
   - 裁判系统数据（参照官方裁判系统串口协议的数据项）：比赛阶段与剩余时间、自身血量 / 等级、
     枪口热量与上限 / 冷却、底盘功率与缓冲能量、允许发弹量、实测弹速、受击装甲与伤害类型、
     增益与所在增益点、己方各单位血量、基地 / 前哨站状态、经济；
   - 视野内目标：相机视场内、未被地形遮挡、在识别距离内且朝向相机的装甲模块——队伍、兵种编号、
     装甲编号、相对位置（距离 / 方位 / 俯仰），带可配置的噪声、帧率与延迟；**不提供对方血量等看不到的信息**；
   - 可选激光雷达扫描；己方雷达标记到的对方位置；队友通信。
2. **控制接口**：底盘速度指令（前后 / 左右 / 旋转，可选相对底盘或相对云台）、云台角度或角速度指令、
   发射指令（单发 / 连发频率）、与裁判系统的交互（兑换发弹量、复活确认、哨兵姿态等）。
   指令经过执行机构模型：加速度、功率、云台转速、射频、热量锁定等限制照常生效。
3. **传输与节拍**：本机 TCP + 逐行 JSON，任何语言都能接入。两种运行方式：
   - 同步（lockstep）：仿真等所有控制程序给出指令再前进，结果可复现，便于调试；
   - 实时：仿真按真实时间推进，指令晚到就沿用上一条，贴近实车。
4. **SDK 与示例**：Python 客户端库与示例（定点巡逻、自瞄射击、键盘遥控），一个 C++ 客户端示例，
   协议文档 `field_sim/CONTROL_API.md`。
5. **规则接入**：伤害、热量、功率、等级属性、战亡与复活、基地 / 前哨站与胜负判定使用已有的规则模块；
   未接入的机制在文档里列明。
6. **页面**：`field.html` 显示各机器人的控制来源、状态与视野，支持同局内人工 / 外部代码混合控制。

验收：示例控制程序只依靠接口数据即可完成巡逻、发现并击打目标；看不到的对手不会出现在数据里；
同步模式下同一配置与同一控制程序两次运行结果一致；断线、超时、非法指令都有明确处理且不破坏对局。

## 不在本阶段范围内

- 第一视角图传画面渲染；空中系统、飞镖与雷达的实体仿真（仍可通过规则实验对局观察其机制）；
- 不可信代码的安全隔离（外部控制程序与本机服务通过 TCP 通信，但服务仍只面向本机可信使用）；
- 轮胎 / 悬挂级别的刚体动力学；本阶段使用 2.5 维底盘模型，假设与限制写入 `field_sim/README.md`。
