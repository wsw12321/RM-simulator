# Adjudicated scenario and event log formats, version 1

This file specifies an **engineering adapter**, not official RMUC event timing.
The inputs are **MANUALLY SUPPLIED ADJUDICATED FACTS**. The assertion is supplied
by the author and is not verification that a referee accepted the facts.

## Scenario JSON

All named keys are required. Unknown keys, duplicate JSON keys, numeric floats,
NaN/infinity, booleans in integer fields, nesting beyond 32 container levels,
non-UTF-8 input and invalid enums are
rejected. JSON object key order and whitespace are irrelevant; array order is not.
Optional *values* are explicit `null`, never omitted or defaulted to zero.

Top-level fields:

- `schema`: `rmuc2027-adjudicated-scenario-v1`.
- `scenario_id`: 1–80 ASCII letters, digits, dot, underscore or hyphen.
- `description`: nonempty text, up to 2048 Unicode characters.
- `fact_status`: literal `MANUALLY_SUPPLIED_ADJUDICATED_FACTS`.
- `ordering_policy`: literal `listed_atomic_boundaries_credits_before_snapshot`.
- `timing_policy`: literal `explicit_milliseconds_no_sampling_or_accrual`.
- `control_source`: `external_totals` or `manual_one_second_credits`.
- `events`: 1–4096 boundary objects, in author-supplied order.

Each boundary has:

- `sequence`: consecutive integer starting at 1, including rejected attempts.
- `elapsed_ms`: integer 0–420000, nondecreasing over **all supplied attempts**.
  Equal timestamps are allowed and retain list order. No time is generated.
- `source_note`: nonempty text up to 2048 characters describing the author-supplied
  basis, unresolved issues or synthetic fixture assumptions.
- `credits`: array of already-adjudicated one-second credit facts, defined below.
- `snapshot`: object with `red`, `blue`, `referee_ruling`, and
  `simultaneous_destruction_resolved`.

The two team objects each require:

- `base_hp`: integer 0–9223372036854775807.
- `attack_damage`: integer in the same range, or `null` for unresolved/not supplied.
  This is the already adjudicated attack-damage total, **not HP loss**.
- `surviving_robot_hp`: integer in the same range, or `null`. This is the already
  adjudicated sum of qualifying living robots' current HP, excluding base/outpost.
- `control_score`: integer in the same range or `null`, **only and obligatorily
  in `external_totals` mode**. It is prohibited in manual-credit mode, even if
  null or equal to the ledger, to prevent ambiguous sources of truth.

`referee_ruling` is `none`, `round_forfeit` or `other`. The latter two are legal
inputs that produce the module error `UnsupportedRefereeRuling`, not simulated
penalties. `simultaneous_destruction_resolved` must be a boolean. A true value is
an explicit upstream claim; it is not a verified real-referee simultaneity ruling.

### Exactly one control-score source

`external_totals` requires every `credits` array to be empty. Supplied control
scores are passed unchanged, including null. There is no active manual ledger.
The adapter does not prove that external cumulative totals are complete,
correctly attributed or monotonic; complete boundary values are authoritative
inputs for this formula experiment.

`manual_one_second_credits` starts a separate ledger at `[0, 0]`. Every event
must omit both `control_score` keys. The ledger is its **sole** control-score
source. Empty credits preserve current totals; they do not accrue points as time
passes. Never use this mode for an incomplete credit history: zero means no
accepted supplied credits, not an unknown official score.

A credit has exactly `sequence` (integer 1–18446744073709551615) and `control`.
Credit sequences must start at 1 and follow the last **committed** credit by 1;
a gap or duplicate is a logged module error. A rejected transaction consumes no
credit sequence. `control` contains exactly `red_outpost`, `blue_outpost`,
`red_base`, `blue_base`. Each position has exactly `controller` (`red` or `blue`)
and `degree` (`temporary` or `full`). Invalid enemy full-base control is a logged
module error. All four values are supplied per credit; no ownership is inferred,
remembered between credits or generated by physical occupancy.

There may be up to 8192 credits across a scenario. This and the 4096-event limit
are defensive resource limits, **not official game constraints**. Credits may be
batched at one boundary. Each claims one externally adjudicated one-second
credit; boundary time is its delivery/settlement position in this supplied order.
The adapter neither validates nor generates a credit's real interval, first
scoring instant, cadence, subsecond remainder, or number of elapsed seconds.

## Atomic boundary processing

1. Validate the complete scenario before starting the native execution. Malformed
   JSON/schema, out-of-range values, boundary numbering/time regression, mode
   conflicts, and resource-limit violations reject the **whole input**, produce a
   JSON diagnostic on stderr and no event log. They never partially execute.
2. Copy the active judge and ledger. If already terminal, reject the boundary with
   `AlreadyFinished` **before any credit is attempted**.
3. In the listed credit order, apply the supplied credit facts to the candidate
   ledger. A failure rejects the entire boundary, including earlier successful
   candidate credits in that boundary. Remaining credits are not attempted.
4. Build the full boundary snapshot. External mode uses supplied totals unchanged;
   manual mode fills control scores from the candidate ledger. No previous team
   facts are carried forward. Invoke the unchanged C++ `MatchJudge`.
5. A module error rejects the whole boundary, leaving clock, ledger and judge
   unchanged. A successful ongoing decision commits the candidate. A terminal
   decision commits the candidate and seals its ledger **in the same transaction**.
6. Continue processing supplied later attempts for audit, even after an error or
   terminal result. Rejected attempts cannot revise the terminal snapshot.

Credit-before-snapshot ordering is a **mandatory, explicit author-selected
adapter policy** and does not assert that the official referee uses that order.
The caller must settle genuine same-time disputes upstream and submit the right
boundary; this adapter does not choose between possible official histories.
No intermediate capture/HP changes are simulated between complete snapshots.

## Deterministic event log JSON

`schema` is `rmuc2027-adjudicated-event-log-v1`.

- `identity` embeds harness/scenario/log/protocol versions, SHA-256 hashes of
  listed implementation files, their aggregate hash, compiled-in native identity,
  and the complete rule module's provenance (including source/manual hash,
  audited-matrix hash, cited rows and unresolved scope).
- `scenario` embeds the complete validated input, including source notes;
  `scenario_sha256` fingerprints its canonical encoding.
- `records` retains every supplied event in order, sequence, `before`/`after`
  state, `credit_attempts`, `resolved_snapshot` (null if evaluation was not
  reached), and either `decision` or explicit `error` and `error_source`.
- `credit_attempts` reports candidate values, **not independently committed
  scores**. Only an accepted boundary commits them. A rejected boundary always
  has identical before/after state. Unattempted credits remain in `supplied`.
- A decision records `outcome`, `reason`, and module `rule_id`. A state records
  the accepted clock, terminal latch, final decision/snapshot and manual ledger
  totals/credit sequence/sealed status; `ledger` is null in external mode.
- `final_state` and `summary` include final terminal status and accepted/rejected
  counts. A terminal result with rejected attempts is still an error-containing
  scenario. An accepted ongoing scenario is not falsely labeled completed.
- `log_sha256` hashes the log excluding that field.

Canonical encoding is Python JSON with sorted keys, comma/colon separators,
ASCII escapes, no NaN or floats, no terminal newline. It contains no ambient
wall-clock timestamp, absolute local path, compiler path, random seed or run ID.
Emitted files use stable sorted, indented JSON for review. Hashes detect drift;
they are **not signatures or referee authenticity proofs**. An attacker can
rewrite both data and hashes.

Before execution the adapter requests the driver's compiled-in identity and
rejects mismatch with current source/provenance hashes. It checks the returned
identity again after execution. Preserve the matching source tree and rebuild
it to replay an older log. This source fingerprint is not a compiler or binary
attestation and does not prove cross-platform determinism.

`verify` checks digest, schema, current identity and then re-executes the embedded
scenario, comparing the **entire** canonical log, including errors and final
state. `extract` first performs that same verification and then emits the embedded
scenario. There is no permissive/import-any-version mode. Logs from other source
builds are rejected rather than silently migrated.

Scenario files are capped at 8 MiB; logs at 32 MiB. The exact ASCII-escaped,
indented output bytes are checked against the corresponding limit **before**
opening an output file or writing stdout. Unicode escaping/indentation may
expand valid input, so an otherwise valid large run or extraction can fail with
`OutputResourceLimit` and no partial output. Every successfully emitted file
fits the next command's input byte limit. The native subprocess has a
15-second timeout. These are engineering safeguards, never match-loss rulings.
The Python JSON boundary does not use JavaScript numbers; signed/unsigned limits
above are exact even above 2^53. Other editors must preserve those integer values.
